## CRITICAL

### TYP-01 (CRITICAL, NEW): a symbol read before its declaration is type-checked has `UnknownType`, and `UnknownType` is assignable to every type; this lets wrongly typed programs through and causes miscompiles

**What is wrong.** Name resolution defines every symbol with `type=UNKNOWN`
(`name_resolution.py:126-488`). The type checker fills a global constant or
variable's type only when its declaration is visited, in source order
(`type_checker.py:183-185`). Function bodies above the declaration read
`symbol.type` directly (`type_checker.py:1184-1187`, `return symbol.type`) and get
`UNKNOWN`. `UnknownType.is_assignable_to` returns `True` for any target
(`types.py:520-522`), and `_is_numeric_compatible`/`_is_integral_compatible`/
`_types_are_comparable` accept `UnknownType` (`type_checker.py:3021-3029`). The
same happens inside a block when an outer name is used before an inner shadowing
declaration, because the lookup finds the inner, not-yet-visited symbol.

**Evidence (all probes in `tmp/audit/compiler/types/probes/`).**
- `v17_forward_string_const_print` (run-allowed): `show` prints `GREETING`, and
  `GREETING :: "hello"` is declared after `show`. a7=0, zig=0. Emitted
  `__a7_stdout_print("{any}\n", .{GREETING});`. Debug and ReleaseFast both print
  `{ 104, 101, 108, 108, 111 }`. Control `v18_backward_string_const_print`
  (declared first) emits `{s}` and prints `hello`. **Silent wrong output that
  depends only on declaration order.**
- `v19_forward_float_const_to_int` (run-allowed): `n: i32 = RATE` with
  `RATE :: 2.0` declared later. a7=0, zig=0, prints `2`. SPEC A.2
  (`docs/SPEC.md:2070`): "No implicit conversions except: ..." The same assignment
  with `RATE` declared first is rejected, like `a44_float_literal_to_int_var`
  (a7=6).
- `v01_forward_const_ret_mismatch` (`ret K` from `fn() string`, `K :: 5` later):
  a7=0; zig=1 "expected type '[]const u8', found 'comptime_int'". Control `v03`
  (K first): a7=6 "Return type mismatch".
- `v02_forward_global_var_mismatch`, `v10_forward_const_in_generic_mapping`,
  `v14_forward_global_cast` (`ret G` as `u8` with `G: i32 = 300`),
  `v15_forward_global_ref_arg` (forward `G: i32` passed to `ref i64`; emitted
  `bump(&G)` against `?*i64`), `p08_ref_local_assign_unknown_forward`: all a7=0,
  zig=1.
- Shadowing variant: `s01_use_outer_before_inner_shadow`
  (`x: i32 = 1; { y: string = x; x := "s" }`), `s02` (`x + 1` on an outer string),
  `s03` (a parameter used before a local shadow): all a7=0, zig=1 with
  "expected type '[]const u8', found 'i32'" and similar. B10 (KNOWN) also makes Zig
  reject these outputs. INFERENCE: once B10 is fixed, the `{any}` formatting
  miscompile from `v17` applies to them too.

**Fix direction.** Give every global constant, variable and alias a type before
any function body is checked: type globals in a dependency-ordered pre-pass, like
`register_function_signature`. Treat `UnknownType` as an error sink. It should not
be assignable, and the checker should report "type not yet known" or
"used before declaration" instead of accepting. Do not reuse an inner scope's
symbol for uses that come before its declaration. **Changes accepted programs
Zig builds:** yes (`v17` and `v19` compile and run today).

## HIGH

### TYP-02 (HIGH, NEW; extends KNOWN MS-7 / G4): the recursion ban has several bypasses that compile and build with Zig

**What is wrong.** `_collect_function_calls` only records calls whose callee is a
bare identifier (`semantic_validator.py:803-818`). Aliases are recorded only for
`name := top_level_function` (`:1098-1104`), and not for alias-of-alias. The
higher-order model follows exactly one trampoline level (`:737-784`). Any
indirection outside those shapes adds no call-graph edge. SPEC 6.2
(`docs/SPEC.md:721-724`) says "Semantic validation also rejects common indirect
cycles through local function-pointer aliases and higher-order callback
trampolines".

**Evidence.** Each probe is a self-recursive `f` with a base case, called from
`main`. All give a7=0 and zig=0. None was run.
- `r09_alias_chain`: `a := f; b := a; ret b(n - 1)`. This is the documented local
  alias case, with one more hop.
- `r02_two_level_trampoline`: `f -> apply2(f) -> apply1(cb) -> cb(n)`.
- `r12_callback_param_alias_in_trampoline_forward`: `apply2` does `c := cb` and
  passes `c` to `apply1`.
- `r03_array_of_fn`: `fs: [1]fn(i32) i32 = [f]; ret fs[0](n - 1)`.
- `r13_array_fn_param_elem`: `run([f], n - 1)`, where `run` calls `fs[0](n)`.
- `r06_fn_returning_fn`: `get :: fn() fn(i32) i32 { ret f }`, then `h := get(); h(n-1)`.
- `probes_mod/m02_module_trampoline`: `helper2.apply(f, n - 1)`, with `apply`
  defined in an imported file (callee is a field access).
- KNOWN MS-7 shapes, re-confirmed: `r05_struct_field_ms7` (`o.op(n - 1)`) and
  `r10_callback_via_struct_arg`.
- Correctly rejected: `r08_alias_reassigned_later`, `r11_generic_trampoline`, and
  `probes_mod/m01_module_self_recursion`.

**Fix direction.** Build call-graph edges from types instead of syntax: treat any
call through a value of function type as a possible call to every top-level
function whose address escapes with a compatible signature, or forbid stored and
returned function values (gate G4 options a and b). **Changes accepted programs
Zig builds:** yes. Needs owner approval (G4).

### TYP-03 (HIGH, NEW): recursion-cycle search is exponential; a 200-line valid program takes 50 s

**What is wrong.** `_find_recursion_path` (`semantic_validator.py:534-544`) runs a
DFS that copies `path + [callee]` and keeps no visited set. It enumerates every
simple path from every function, and does this once per function
(`:521-524`).

**Evidence.** `types/perf/gen.py L` generates L layers of two functions, each
calling both functions of the next layer (no recursion). `types/perf/timing.out`,
`uv run a7 layers_L.a7 --mode semantic`, all exit 0:
L=12 0.2 s, 16 0.4 s, 18 0.9 s, 20 3.0 s, 22 11.6 s, 24 49.8 s (`layers_24.a7`
is 200 lines). `prof.py` on L=20 attributes 9.0 s of 9.04 s to
`_find_recursion_path` (43 calls). Extrapolated (INFERENCE): L=30 takes about an
hour.

**Fix direction.** Use Tarjan or Kosaraju SCC detection (linear time). Report one
diagnostic per non-trivial SCC or self-loop. **Changes accepted programs:** no.

### TYP-04 (HIGH, NEW): SPEC 7.1 inline generic functions pass semantic analysis but fail codegen with exit 7; generic bodies are never checked per instantiation

**What is wrong.** Inside a generic body every operator accepts `$T`
(`type_checker.py:3021-3029`). Bodies are checked once against the opaque
parameter and never again after `generic_mapping` is computed
(`type_checker.py:1354-1362`). Constraints only restrict call arguments. They do
not restrict what the body may do. Conflicting inferences are dropped silently:
`bind` keeps the first binding and ignores a conflicting later one
(`type_checker.py:1589-1592`). The worklist pops the last argument first.

**Evidence.**
- `g02_spec71_inline_identity` is the SPEC 7.1 form
  `identity :: fn(x: $T) $T { ret x }` called with `identity(7)`
  (`docs/SPEC.md:884-887`). a7=7: "Zig backend: generic type requires an explicit
  generic environment". The same happens in `e30_generic_two_calls_different_T`,
  `e12`, `e14`, `e21`, `e24` and `e28`. The semantic tests accept this form
  (`test_semantic_generics.py:115-128`). SPEC 7.4's declared form
  `identity($T) :: fn` compiles (`g01`, zig=0).
- Declared form, body not re-checked: `g03_declared_T_body_mul_string`
  (`dbl("hi")` with body `a * 2`): a7=0, zig=1 "incompatible types: '[]const u8'
  and 'comptime_int'". `g04_declared_T_bool_lt` (`<` on bool): a7=0, zig=1.
- `g05_declared_T_mixed`: `add(x_i32, y_f64)` with `a: $T, b: $T`. a7=0, emitted
  `add(f64, x, y)`. A7 never reports that `$T` was inferred as both `i32` and `f64`.
  `e11_generic_same_T_conflict` blames Argument 1 because `$T` was bound from
  argument 2.
- `g06`/`g10` (`z: $T = "str"` or `= 0`, allowed by the relaxation at
  `type_checker.py:695-713`) give a7=7.
- `u05_nil_arg_generic` (`id(nil)`) gives a7=7.

**Fix direction.** Check each concrete instantiation's body with the mapping
applied, or restrict the body to operations the declared constraint guarantees.
Report conflicting bindings. Accept the inline form end to end, or document it as
unsupported. **Changes accepted programs Zig builds:** yes for `g05`. `g02` and
`e30` only start compiling.

## MEDIUM

### TYP-05 (MEDIUM, NEW): compound-assignment operator checks are dead code

`visit_assignment` reads `getattr(node, 'op', None)` (`type_checker.py:862`).
Assignment nodes store the operator in `operator` (`ast_nodes.py:419`
`kind=NodeKind.ASSIGNMENT, target=target, operator=op`). The numeric and integer
checks at `:863-872` never run. Only plain assignability is checked.
Probes: `b34_compound_add_string` (`a += b` on strings), `c35_compound_shl_float`
(`<<=` on f64), `c36_compound_add_bool` (`+=` on bool): a7=0, zig=1 ("invalid
operands", "bit shifting operation expected integer type").
`c37_compound_mod_string` is rejected only by the safety pass, with the misleading
message "division/modulo divisor must be non-zero". Fix: read `node.operator`.
Changes accepted programs Zig builds: no (Zig already rejects these).

### TYP-06 (MEDIUM, partly KNOWN G3 "mixed operand widening"): binary-operator result types are wrong and mixed operands are accepted

`visit_binary_expr` returns the left operand's type for integers and the first
float operand's type (`type_checker.py:1222-1227`). It never requires the
operands to match. Bitwise operators return `left_type` (`:1251`). Unary `-`
accepts unsigned operands (`:1261-1264`). Probes (a7=0, zig=1 unless noted):
- `c07_add_u8_i32_params` (`ret a + b` as u8): Zig peer type is i32.
- `c09_add_f32_f64_params`, `c10_result_type_left_u8`, `c13_bitand_mixed_widths`.
- `c24_int_float_compare` (`i64 < f32`): "expected type 'f32', found 'i64'".
- `c11_neg_unsigned_param` (`-a`, `a: u32`): "negation of type 'u32'" (NEW).
- `c48_neg_u8_literal_expr` (`a * -1`, `a: usize`).
- Asymmetry: `c46` `ret a + 1` (u8) gives a7=0, but `c47_literal_left_u8_right`
  `ret 1 + a` gives a7=6 "expected 'u8', got 'i32'" (NEW).
- `c14_shift_by_signed` (`a << b`, `b: i32`) builds as `@intCast(b)`, which panics
  or is undefined for negative `b` (KNOWN G3 shift-count row).

Fix: one numeric-operator rule (same type, or an approved widening, plus
contextual literals). Changes accepted programs Zig builds: yes (`c41`/`c42` mixed
widths build and run today). Needs G3.

### TYP-07 (MEDIUM, NEW): implicit integer-to-float and integer widening contradict SPEC A.2 and accept conversions Zig rejects

`PrimitiveType.is_assignable_to` allows any integer to any float
(`types.py:137-138`), plus signed and unsigned widening (`:120-131`). SPEC A.2
(`docs/SPEC.md:2070-2073`) allows only array to slice, `T` to `ref T` in calls,
and in-range integer literals. Zig accepts only lossless integer-to-float at run
time, so i64 and u64 to f64 and i32 to f32 are rejected. Probes, a7=0 and zig=1:
- `b01_i64_param_to_f64`, `b02_i32_param_to_f32`, `b03_u64_param_to_f64_arg`
- `c40_compound_add_i64_to_f64`
- `b04_match_expr_runtime_int_float` ("incompatible types: 'i64' and 'f64'")
- `c43_minmax_mixed` (math.min(i64, f32))
- `a02_i64_to_f32_implicit`

The widening that works (`a03`-`a08`, `c38`, `c39`) contradicts the SPEC's "no
implicit conversions" text. `u32 -> isize` is assignable on the assumption that
`isize` is 64 bits (`types.py:129-131`; also `cast_classifier.py:30-31`), which
is wrong on 32-bit targets (INFERENCE; not tested). Fix: decide the rule (G3) and
make SPEC, `is_assignable_to` and the cast classifier agree. Changes accepted
programs Zig builds: yes.

### TYP-08 (MEDIUM, NEW): SPEC A.2 "array to slice" implicit conversion is not implemented

`ArrayType` has no `is_assignable_to` override, so assignability is exact
equality. `a10_array_to_slice_arg` (`first(arr)` with `xs: []i32`) gives a7=6
"Argument type mismatch: expected '[]i32', got '[3]i32'", and
`a11_array_to_slice_var` gives a7=6. SPEC A.2 line 2071: "Array to slice (safe
widening)". Fix: allow `[N]T -> []T` for lvalue arrays (with lifetime checks) or
drop the SPEC line. Changes accepted programs: no (only accepts more).

### TYP-09 (MEDIUM, NEW; string case KNOWN B3): `==`/`!=` accepted for structs, arrays, unions and slices

`_types_are_comparable` returns true whenever `left.equals(right)`
(`type_checker.py:3032-3033`). Probes, a7=0 and zig=1 "operator == not allowed":
`b17_struct_eq`, `b18_array_eq`, `b20_union_eq`, `d49_array_eq_literal`.
`b19_slice_eq` is also accepted (Zig failed earlier, on the argument). Fix: allow
equality only for scalar, enum, bool, reference-vs-nil and function values.
Changes accepted programs Zig builds: no.

### TYP-10 (MEDIUM, NEW): `nil` is typed `UnknownType` and passes every check outside declarations, returns and arguments

`visit_literal` returns `UNKNOWN` for `nil` (`type_checker.py:1175-1176`). Only
var-decl, return, argument and initializer paths test `_is_nil_literal`.
Probes, a7=0 and zig=1:
- `b28_nil_arith` (`nil + 1`)
- `u04_nil_compare_int` (`x_i32 == nil`)
- `u09_nil_in_array_literal`
- `u13_nil_if_expr` (`y: i32 = if k { nil } else { nil }`)
- `u15_nil_unary` (`-nil`)

The reverse also happens: `p02_ref_local_reset_nil` (`r: ref i32 = nil; r = nil`)
gives a7=6 "Assignment type mismatch: expected 'i32', got 'unknown type'", because
`visit_assignment` treats `nil` as a value to write through the reference
(`:834-841`). Whether `r = nil` should rebind is a design question (UNVERIFIED
intent). Fix: give `nil` its own type, assignable only to `ref T`. Changes
accepted programs Zig builds: no for the accepted cases.

### TYP-11 (MEDIUM, NEW; completeness is gate G5): struct literals are not validated

`visit_struct_init` skips unknown field names (`expected_type` stays `None`,
`type_checker.py:2763-2785`). It never checks missing or duplicate fields, and it
does not type-check positional initializers. Probes, a7=0 and zig=1:
- `d01_struct_unknown_field_init` ("no field named 'z'")
- `d02_struct_missing_field_init`
- `d03_struct_duplicate_field_init`
- `d05_struct_positional_wrong_type` (`Pt{"a", 2}`)
- `d06_struct_positional_too_many`

A non-struct, non-union type name returns `UNKNOWN` with no error
(`:2736-2737`): `a31_enum_struct_init` and `a32_unknown_struct_init_flows`
(`Color{r: 1}`, then `x: i32 = c`, `y: string = c`) give a7=0, zig=1. Generic
union literals ignore type arguments: `h01_spec72_generic_union` (SPEC 7.2
`Result(i32, string){ok: 1}`) gives a7=6 "expected '$T', got 'i32'". Fix: validate
names, duplicates, arity and positional types, and report non-struct targets.
Changes accepted programs Zig builds: no.

### TYP-12 (MEDIUM, NEW): type names, enum values and module members are accepted as values or in field positions

`visit_identifier` returns the symbol's type for any symbol kind
(`type_checker.py:1184-1187`). `visit_field_access` then treats `StructType` and
`EnumType` receivers the same whether they are a type or a value
(`:1805-1824`). Probes, a7=0 and zig=1:
- `a29_struct_type_field_as_value` (`v := Point.x`)
- `a30_type_name_as_value` (`p := Point; q := p.x`)
- `p12_type_alias_used_as_value` (`h := Handle`)
- `a28_unknown_type_field_on_enum_value` (`c := Color.Red; d := c.Green`)
- `u01_io_println_value` (`p := io.println; x: i32 = p`, UNKNOWN flow)
- `a33_empty_array_literal_flows` (`x := []; y: i32 = x`: empty array literal is
  UNKNOWN, `:2852`)
- `u07_empty_array_arg`

Fix: separate type symbols from value symbols in expression position, and give
`[]` a diagnostic or a contextual type. Changes accepted programs Zig builds: no.

### TYP-13 (MEDIUM, NEW): `match` accepts scrutinees and patterns that Zig `switch` rejects; the redundancy checker folds constants with Python semantics

- Scrutinee types are unrestricted. `d13_match_string_scrutinee` (zig "cannot
  switch on strings"), `d19_match_float_scrutinee` and `d20_match_struct_scrutinee`
  give a7=0, zig=1.
- Exhaustiveness is checked only for bool and enum (`type_checker.py:2694-2720`).
  `d21_match_expr_no_else_int` (int match expression without `else`) gives a7=0,
  zig=1 "switch must handle all possibilities".
- Reversed ranges are silently normalized with `min`/`max` (`:2193-2195`).
  `d16_match_range_reversed` (`case 10..1`) gives a7=0, zig=1.
- `_range_const_expr_value` uses Python `//` and `%` (`:2317-2322`), while
  folding and run time truncate. `d17_match_range_neg_div_const`
  (`A :: -7 / 2`, `case -3` and `case A..A`) and `d18_match_range_neg_mod_const`
  give a7=0, zig=1 "duplicate switch value" (missed duplicate).
  `e03_match_range_false_redundant` (`case -4` then `case A`) gives a7=6
  "redundant match pattern 'A'" on a valid program (false rejection).
- Duplicate enum tag values and variants are accepted:
  `d10_enum_explicit_values_dup`, `p09_enum_value_nonliteral` (`A = 1 + 1, B = 2`;
  a non-literal value is recorded as `None`, `:346-348`) and
  `p17_duplicate_enum_variants` give a7=0, zig=1.

Fix: restrict scrutinee types, require `else` for non-enum and non-bool match
expressions, reject reversed ranges, use the preprocessor's truncating folder,
validate enum values. Changes accepted programs Zig builds: no, except `e03`
(currently rejected).

### TYP-14 (MEDIUM, NEW): implicit `ref` arguments are approved for non-writable lvalues and for widened types

`type_checker.py:1392-1395` marks an argument `implicit_ref_args` when
`arg_type.is_assignable_to(param_type.referent_type)` and the node kind is
identifier, field, index or deref. The check ignores mutability, rvalue roots and
exact type identity. Probes, a7=0 and zig=1:
- `f16_implicit_ref_widen` (`i32` local to `ref i64`; emitted `inc(&x)` against
  `?*i64`, "expected type '?*i64', found '*i32'")
- `f14_implicit_ref_const` (a `::` constant)
- `f15_implicit_ref_param_value` (a by-value parameter)
- `f17_implicit_ref_for_capture`
- `f13_implicit_ref_rvalue_field` (`inc(mk().x)`)

INFERENCE: `f16` would be an 8-byte write into 4-byte storage if the backend ever
emitted a pointer cast. Today Zig's type check is the only barrier. Fix: require
exact referent type identity and a mutable root. Changes accepted programs Zig
builds: no.

### TYP-15 (MEDIUM, partly KNOWN B7/B8): mutability is checked only for bare identifier targets

`visit_assignment` checks `is_mutable` only when the target is an `IDENTIFIER`
(`type_checker.py:851-859`). Field and element writes on immutable roots pass.
NEW: `p03_const_struct_field_write` (`P :: Pt{x: 1}` at file scope, `P.x = 5`) and
`p04_local_const_struct_field_write` give a7=0, zig=1 "cannot assign to constant".
KNOWN (B7 family): `f07_param_field_assign`, `f08_param_array_elem_assign`
(B7), `f12_for_in_capture_field_assign` (B8). Fix: walk the lvalue to its root
and check root mutability, except through `ref`. Changes accepted programs Zig
builds: no.

### TYP-16 (MEDIUM, NEW): struct field types that name later declarations, and self-referential `ref` fields, resolve to `UnknownType`, so valid programs are rejected

`register_type_decl` runs in source order (`type_checker.py:174-176`). A field
type naming a struct, enum or union declared later, or the struct itself, reads
`symbol.type == UNKNOWN` (`:451`). Probes, a7=6:
- `v04_struct_field_forward_type`: "expected 'unknown type', got 'B' (Field 'b')".
- `v08_forward_enum_in_struct`, `v09_forward_union_field`.
- `v05_recursive_struct_field_unknown`: "got 'ref unknown type'".
- `v06_recursive_struct_deref_field` (`nx.value` on `ref Node`): "Cannot access
  field on non-struct type: got 'ref unknown type'".
- `v11_recursive_struct_ref_assign` (`p: ref Node = n.next`): "expected 'ref Node',
  got 'ref unknown type'".

A linked list cannot follow `next`. The companion unsoundness (`s: string = a.b`
typed UNKNOWN) belongs to TYP-01. Fix: create nominal type objects first, then
fill fields. Changes accepted programs: no (only accepts more).

### TYP-17 (MEDIUM, partly KNOWN T1): array sizes that are not literal integers become `None`, and every `None`-sized array type is equal

`resolve_type_node` uses `extract_int_value`, which only reads integer literals
(`type_checker.py:397`, `:380-384`). `ArrayType.equals` compares `size`, so
`None == None` (`types.py:160-163`; `mono.out`: "ArrayType size None equals
True [None]i32"). Probes:
- `e01_array_const_sizes_differ` (`N :: 2`, `M :: 5`, `b: [M]i32 = a` with
  `a: [N]i32`): a7=0, zig=1 "expected type '[5]i32', found '[2]i32'".
- `e02_array_const_size_param`: same result.
